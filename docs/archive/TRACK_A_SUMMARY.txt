A1: OPERATION STATE MANAGEMENT
===============================
File: js/alchemical_integration.js

Class: FurnaceOperation
  - Tracks a single furnace operation through its entire lifecycle
  - Constructor(operationId, materials, targetTemp)

  Properties:
    operationId   : 'calcination', 'dissolution', etc.
    materials     : [{ id: 'vitriol', qty: 3 }, ...]
    targetTemp    : 20-200 degrees Celsius
    progress      : 0-100%
    duration      : 3000ms (configurable)
    status        : 'running' | 'completed' | 'aborted' | 'failed'
    dangers       : [] (for Track B integration)
    currentTemp   : actual furnace temperature during operation
    fuel          : charcoal remaining
    startTime     : timestamp for duration calculation

  Methods:
    tick(dt)          : Advance operation by dt milliseconds
    getStatusText()   : Return human-readable state
    abort()           : Stop operation (materials lost)
    fail()            : Mark operation as failed

Key Design:
  - Deterministic progress (based on time, not RNG)
  - Simplified temperature simulation (good enough for display)
  - Separated from Furnace class (state vs. physics)
  - Ready for Track B danger integration


A2: FURNACE UI PANEL
====================
File: js/ui.js

Function: renderFurnacePanel(ctx, x, y, operation, furnace)
  - Renders 320x280px Dragon-Warrior style panel
  - Updates every frame with operation data

Displays:
  1. Operation name (e.g., "FURNACE OPERATION")
  2. Temperature gauge
     - Shows current vs. target in °C
     - Color-coded: blue (cold) -> orange -> yellow -> red (hot)
     - Fills proportionally based on 0-200°C range
  3. Fuel bar
     - Shows charcoal remaining (0-100%)
     - Brown color (#8b6f47)
  4. Progress bar
     - Shows operation completion (0-100%)
     - Green color (COLORS.hpGreen)
  5. Estimated time remaining
     - Calculated from operation.duration and elapsed time
     - Format: "5m 30s" or "45s"
  6. Materials list
     - Shows what's in crucible: "3x Vitriol", etc.
     - Indented, dimmed for readability

Code Quality:
  - Uses existing ui.js utilities (window9, text, bar, COLORS)
  - No external dependencies
  - Efficient: single render call per frame
  - Safe: null-checks on materials array


A3: INTEGRATION INTO MAIN GAME LOOP
===================================
File: js/main.js

Imports Added:
  - import { FurnaceOperation } from './alchemical_integration.js'
  - import { ..., renderFurnacePanel } from './ui.js'

Game Class Properties Added:
  this.activeOperation = null   // current FurnaceOperation
  this.activeFurnace = null     // reference to furnace running it

Update Loop Changes (update(dt) method):
  - Each frame: checks if activeOperation exists and status is 'running'
  - Calls activeOperation.tick(dt) to advance operation
  - Detects completion when progress >= 100
  - Logs completion message to message box
  - TODO (A4): Hook to quest system

Render Loop Changes (render() method):
  - After all other rendering, checks if activeOperation && activeFurnace
  - Calls renderFurnacePanel(ctx, W-340, 20, operation, furnace)
  - Panel appears in top-right corner, non-intrusive

New Method: startFurnaceOperation(operationId, targetTemp, materials)
  - Creates mock Furnace object if needed
  - Instantiates new FurnaceOperation
  - Stores in game state (this.activeOperation, this.activeFurnace)
  - Logs startup messages
  - Returns true on success, false on failure

UI Integration:
  - _showFurnaceMenu(roomId) now calls startFurnaceOperation
  - Connected to castle laboratory menu system
  - Players can start operations: calcination, dissolution, etc.

ARCHITECTURE NOTES
==================
Why FurnaceOperation is separate from Furnace?
  - Furnace (furnace_system.js): manages physical state
  - FurnaceOperation: tracks a specific task
  - Allows multiple operations on different furnaces (future)
  - Cleaner separation of concerns

Why duration is fixed in constructor?
  - Placeholder for testing
  - Will be set from OPERATIONS database in A4
  - Allows predictable test timing

Why danger checking is deferred?
  - Furnace class already has _checkDangers() method
  - A1-A3 focus on state management and UI
  - B1-B4 will integrate danger cleanly
  - Keeps changes focused and testable

Why UI panel is separate from Game class?
  - Follows existing pattern (MessageBox.render, etc.)
  - Easy to test independently
  - Can render from anywhere (future features)
  - No coupling between state and rendering


PERFORMANCE CONSIDERATIONS
==========================
- FurnaceOperation.tick(dt) is O(1) - minimal work per frame
- renderFurnacePanel() is O(materials.length) - scales linearly
- No GC pressure (no arrays created each frame)
- Canvas rendering is hardware-accelerated
- Panel position (W-340, 20) avoids UI overlap
